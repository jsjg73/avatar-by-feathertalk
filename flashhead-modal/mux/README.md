# 한 컨테이너로 여러 라이브 세션

무음 구간을 대기 루프로 재생하게 되자(→ `../spike-seam`, `../spike-return`) GPU는
아바타가 말할 때만 일한다. 그렇다면 한 GPU가 여러 세션을 함께 서빙할 수 있어야 한다.

## 처음 시도(A안)가 실패한 이유

세션마다 자기 벽시계를 가진 스레드를 두고 GPU 락을 다투게 했다. 조율되지 않은
탐욕적 행위자들의 전형적인 병리가 나왔다 — 밀린 세션이 전속력으로 따라잡으려
GPU를 붙잡고, 그 바람에 다른 세션이 밀리고, 다시 전속력으로 다투는 되먹임.

6세션 실측: 4개 세션이 **25~120초 밀렸고** 두 세션은 4분 동안 청크를 36개밖에
만들지 못했다(정상은 250개). 승인 제어·따라잡기 제한 같은 휴리스틱을 덧대도
절반만 나아졌다 — 설계가 틀린 것이지 파라미터가 틀린 게 아니었다.

## B안: 컨테이너당 스케줄러 하나

세션은 경쟁하는 스레드가 아니라 **수동적인 상태 객체**가 된다. 스케줄러 스레드
하나가 0.96초 슬롯마다 **모든 세션의 출력을 직접 만들고**, 이번 슬롯에 GPU를
누구에게 줄지 정한다.

- 세션은 슬롯마다 정확히 한 청크를 받는다 → 남의 밀림이 나에게 전이되지 않는다
- 슬롯당 생성 예산은 측정된 생성 시간에서 나온다(L4에서 0.79s / 0.96s → **1개**)
- 말하려는 세션이 예산을 넘으면 **발화가 한두 슬롯 기다린다**. 영상은 대기 루프로
  계속 흐르므로 절대 멈추지 않는다
- 발화 중인 세션은 문장이 끝날 때까지 우선권을 유지한다(문장을 자르지 않기 위해)
- 오디오 수신은 세션별 스레드가 맡는다 — 스케줄러가 네트워크에서 블로킹되면 안 된다

## 실측 (L4, Lite, 2026-09-17)

| 세션 | 문장 간격 | GPU 점유율 | 영상 실시간 | 발화 대기(중앙/최대) |
|---|---|---|---|---|
| 3 | 18s | 53% | ✓ 129/131 청크, 종료 지연 0.00s | 0s / 22s |
| **6** | 18s | 63% | ✓ 254~264/264 청크, 종료 지연 0.02s | **0s / 13s** |
| 8 | 14s | 84% | ✓ 종료 지연 0.00~0.04s | 0s / **82s** |

- **6세션에서 영상 24.9분을 GPU 3.1분으로** 만들었다(8배). 8세션은 37.3분을 4.8분으로.
- 부하가 걸려도 **영상은 끝까지 실시간**이다. 초과분은 발화 지연으로만 나타난다.
- 8세션(문장 간격 14초)은 발화 수요가 1.71 청크/s로 예산 1.04 청크/s의 **165%**라
  대기열이 발산한다(최대 82초, 계속 증가). 6세션/18초는 1.00 청크/s로 96%라
  대기가 13초에 머문다.

## 용량 규칙

발화 수요 = 세션 수 × 발화 비중 < GPU의 청크 속도(L4 Lite에서 1.04 청크/s ≈ 세션 1개가
쉬지 않고 말하는 양). 여유를 60~70%로 잡으면:

> **세션 수 ≈ 0.65 ÷ 아바타 발화 비중**

발화 비중 14%면 L4 한 장에 **4~5세션**이 편안하고 6세션이 경계다. 이 비중이 용량을
그대로 결정하므로, 실제 면접 대본으로 측정하는 것이 다음 순서다.

재현: `modal run app.py::mux --sessions 6 --minutes 4 --gap-s 18`

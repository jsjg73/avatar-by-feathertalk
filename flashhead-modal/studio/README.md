# FlashHead Studio

아바타를 고르고 멘트를 입력하면 그 인물이 말하는 영상을 만드는 로컬 데모 페이지.

```bash
./studio.sh start      # http://127.0.0.1:8300   (stop | restart)
```

`../app.py`가 `modal deploy` 되어 있어야 한다(앱 이름 `flashhead`).

## 흐름

| 단계 | 어디서 | 무엇 |
|---|---|---|
| 1. 텍스트/음성 파일 → WAV | Mac | `say -v "Yuna (Premium)"`, 또는 **업로드한 오디오**를 ffmpeg로 16 kHz mono 변환 (꼬리 무음은 렌더러가 붙임) |
| 2. WAV → HLS | Modal L4 | 배포된 `Renderer.render_stream.spawn(...)` — 상주 컨테이너에서 `once` 모드로 청크(0.96 s)를 만들고, 컨테이너 안의 ffmpeg가 청크마다 fMP4 세그먼트를 닫는 즉시 `modal.Queue`(파티션 = 잡 id)에 넣음. 진행 줄도 같은 항목에 묶여 옴 |
| 3. 재생 | Mac | 세그먼트를 `jobs/<id>/hls/`에 받아 `/hls/<id>/…`로 서빙, 페이지의 hls.js가 **첫 세그먼트가 오면 바로 재생**. 끝나면 세그먼트를 리먹스(재인코딩 없음)해 `video.mp4`로 저장, 카드에 아바타·경로 + "Finder에서 보기" |

잡은 **한 번에 하나씩** 처리한다 — 동시 실행은 GPU 비용이 배로 든다(`max_containers=1`이라 어차피 직렬).

## 스트리밍 재생 (2026-09-11)

완성된 TTS 파일을 넘기고 결과를 **렌더 중에** 본다. 라이브 대화형이 아니므로 오디오 전체가 처음부터 있고, 립싱크가 더 좋은 `once` 모드를 그대로 쓴다.

- 컨테이너: `ffmpeg -f hls -hls_segment_type fmp4 -hls_time 0.96`, GOP = 24프레임이라 세그먼트 = 청크 하나. `temp_file` 플래그로 세그먼트·플레이리스트가 원자적으로 나타나고, 플레이리스트에 오른 세그먼트는 완성된 것. `init.mp4`는 첫 세그먼트가 플러시될 때(delay_moov) 내용이 채워지므로 그 뒤에만 보낸다(먼저 읽었다가 0바이트를 보낸 적 있음). 프레임은 별도 스레드가 파이프로 넣어 GPU 루프가 인코딩을 기다리지 않는다.
- 전달: Modal **제너레이터(`remote_gen`)는 출력이 5–20 s 늦게 묶음으로 도착**해 플레이어가 굶었다. `modal.Queue`는 put→get 0.6–0.8 s(항목 ≤ 1 MiB, 세그먼트는 ~170 KB). 항목 하나에 한 번의 왕복(~0.5 s)이 들어 청크당 3항목이면 20청크에 ~10 s 뒤처지므로, 청크가 만든 것(로그+세그먼트+플레이리스트)을 **항목 하나로 묶고** 스튜디오는 `get_many`로 한 번에 비운다.
- 스튜디오: 파일을 `.tmp`로 쓰고 `os.replace` → 플레이어가 반쪽 파일을 읽을 일 없음. 플레이리스트는 `Cache-Control: no-store`(자라는 중이라 캐시 금지). `init.mp4 + 세그먼트 1개 + 플레이리스트`가 갖춰지면 `hls_url`이 켜진다.
- 페이지: hls.js(`startPosition: 0`)로 처음부터 재생, 생성(0.82 s/청크)이 재생(0.96 s/청크)보다 빠르니 버퍼가 계속 쌓임. Safari는 내장 HLS 폴백. 비디오 엘리먼트는 그대로 두므로 완료 후에도 재생이 끊기지 않고, EVENT 플레이리스트가 ENDLIST를 받으면 VOD가 되어 탐색도 된다.
- 실측(2026-09-11, 75.3 s 멘트 = 79청크): 컨테이너 렌더 71.9 s(0.91 s/청크, 큐 put 포함), 80세그먼트 13 MB, 재생은 준비된 컨테이너 기준 호출 후 약 4–5 s에 시작(세그먼트 3개). 재생 중 정지 0회·되감김 0회, 버퍼 여유 최소 4.9 s → 종료 시 15 s. 전달 지연 중앙값 ≈0 s, p90 6 s. 콜드면 그 앞에 컨테이너 기동+로딩 60–120 s.
- 큐 put은 별도 송신 스레드가 처리한다(GPU 루프 안에서 동기로 돌릴 때 청크당 0.91 s → 스레드 분리 후 **0.78 s**, 실시간 여유 23%). 전달 지연 p90 0.2 s, 최대 0.9 s.
- 준비 플래그(`flashhead-state["ready"]`)는 컨테이너가 20 s마다 `beat`를 갱신하고, 스튜디오는 60 s 넘게 안 뛴 플래그를 무시한다 — 배포로 컨테이너가 교체될 때 exit 훅이 안 돌아 옛 플래그가 남으면 '준비됨'으로 잘못 보였기 때문.

## 동시 세션 시연 — 전용 화면 `/live`

`http://127.0.0.1:8300/live`. 클립 스튜디오(`/`)와 분리했다 — 세션을 여러 개 띄우면
화면이 꽉 차고, 보려는 것도 다르기 때문이다.

**+ 세션 추가**를 누를 때마다 라이브 세션이 하나씩 늘어난다. 모두 **컨테이너 1대를
공유**하고(`app.py`의 스케줄러 하나가 슬롯마다 모든 세션의 출력을 만든다), 최대 8개다.
각 칸은 라이브 영상과 지표(발화/전체 청크, GPU 비중, 질문 수, 대기 음성)를 보여준다.
칸을 클릭하면 그 세션의 소리가 켜진다(기본은 음소거).

질문 음성은 **한 번만 합성해 `tts-cache/`에 둔다** — 같은 질문이 세션마다 매 주기
반복되는데 `say -v "Yuna (Premium)"` 호출마다 2~3초의 프로세스·음성 기동 비용이 붙기
때문이다. 서버가 뜰 때 질문 8개를 미리 합성해 두므로 첫 질문도 기다리지 않는다.
(키는 음성 + 문장의 해시. 캐시는 추적하지 않는다.)

세션은 **면접 리듬을 자동으로** 돈다 — 아바타가 약 7초 질문하고 35초 기다린다(42초 주기,
`LIVE_SPEAK_S`/`LIVE_CYCLE_S`). 질문은 `INTERVIEW_QUESTIONS`에서 순서대로 나온다.
한국어 40~45자가 Yuna Premium에서 약 7초다(실측).

- 실측(3세션, L4 Lite): 세션당 **GPU 13.8%**, 영상 지연 0.00s, 86% 절감.
  용량 규칙은 `../mux/README.md` 참조 — 발화 16.7%면 L4 한 장에 **4세션**이 편안하다.
### 쌓인다 — 사라지지 않는다

종료한 세션도 화면에 남는다. 칸의 영상은 라이브 스트림에서 **녹화본**
(`live/<sid>/video.mp4`)으로 바뀌어 다시 볼 수 있고, 간트의 그 줄도 그대로 남는다.
서버를 재시작해도 `live/*/session.json`에서 복원한다(구간·녹화·질문 수 포함).
화면을 비우려면 **종료분 정리** — 목록에서만 지우고 파일은 남긴다(`session.json`을
`session.hidden.json`으로 바꿔 다시 복원되지 않게 한다).

### 하단 간트 — GPU 발화 점유

세션마다 한 줄, 가로축은 **시연 전체**(기본). 오래된 구간이 왼쪽으로 흘러나가
사라지지 않는다. **마지막 2분만** 버튼으로 확대해 지금의 경합을 볼 수 있다.

오른쪽 끝은 **진행 중인 세션이 있을 때만 현재 시각**을 따라간다(빨간 선이 지금).
모두 끝났으면 **마지막 발화 지점**에서 멈춘다 — 안 그러면 시간이 흐를수록 차트가
늘어나 데이터가 왼쪽에 쪼그라들고 점유율도 계속 낮아진다(같은 기록이 13% → 37%로
정정됐다). 눈금은 시작으로부터의 경과 시간이다. 칠해진 구간이 **그 세션이 GPU를 쓰며 말한 시간**이다.
한 슬롯에 한 세션만 생성할 수 있으므로 막대가 겹치지 않고 어긋나 배치되는 것이 정상이고,
합계 점유율이 100%에 가까워질수록 질문 시작이 밀린다(용량 규칙은 `../mux/README.md`).

구간은 컨테이너가 찍는 `[ 12.3s] live: chunk N speech …` 로그에서 뽑는다. 각 줄의
컨테이너 경과 시간을 세션마다 한 번 실제 시계에 고정(`container_t0`)해 여러 세션을
하나의 타임라인에 올린다. 발화 청크는 모두 로그에 남으므로 구간이 빠지지 않는다.

- 세션은 30분(`max_seconds`)이 지나면 자동 종료된다. 그 전에 멈추려면 칸의 **종료**나
  헤더의 **전체 종료**.

## 라이브 세션 (단일 세션 시절 설명)

"세션 시작" → 상주 컨테이너가 `Renderer.live()`로 **벽시계에 맞춰 0.96 s 청크를 계속 생성**한다(상류 stream 모드: 8 s 오디오 창, 청크당 24프레임). 문장을 입력하면 스튜디오가 `say`로 PCM을 만들어 0.96 s 조각으로 큐 파티션 `<sid>:audio`에 넣고, 컨테이너는 다음 청크 슬롯부터 그 오디오로 말한다. 오디오가 없으면 무음 청크로 대기(입 다물고 미세 움직임). 세그먼트는 기존 HLS 경로(`/hls/live/<sid>/…`)로 오고 플레이어는 라이브 엣지 1.5 s 뒤를 따라간다. 종료(또는 무음 3분)하면 녹화 `live/<sid>/video.mp4`를 남긴다.

- 실측(2026-09-14, L4 Lite, 91 s 세션·93청크): 청크 생성 0.80–0.85 s(중앙값 0.815), 스케줄 지연 0.03–0.04 s로 고정(벽시계 동기 유지), 문장 8.4 s → 9청크가 정확히 0.96 s 간격으로 소비됨. **"말하기" 클릭 → 컨테이너가 그 음성 청크를 생성한 로그가 스튜디오에 도착**까지 3–4 s(TTS ~1 s + 큐 0.7 s + 슬롯 대기 ≤0.96 s + 생성 0.8 s + 로그 전달). 화면에 보이기까지는 세그먼트 닫힘(+0.96 s)·전송(0.7 s)·플레이어 버퍼(1.5 s)가 더 붙어 **약 6–7 s**.
- **Pro 라이브**(패널의 Lite/Pro 선택): `LivePro` 클래스(2×H100, jp, FA2, `xfuser==0.4.5`, compile OFF)가 컨테이너 기동 시 `torchrun` 2랭크 워커(`live_worker.py`)를 상주시키고, 세션마다 제어 FIFO로 start/오디오/end를 넘긴다. 랭크 0이 페이싱·ffmpeg·상태 파일을 맡고 매 청크 PCM을 브로드캐스트해 두 GPU가 시퀀스 병렬로 계산. 실측(2026-09-14, 89 s 세션·77청크): **청크 생성 0.68 s / 1.12 s 슬롯(1.65×)**, 스케줄 지연 0.00 s 고정, 문장 8.9 s → 8청크가 1.12 s 간격으로 소비, 세션 시작 요청 → 라이브까지 콜드 **~50 s**(2×H100 스케줄 수 초 + Pro 로딩), 말하기 → 음성 청크 생성 3–4 s. 비용 세션 중 2×H100 ≈ $8/hr, 마지막 세션 후 5분 뒤 종료.
- 문장은 **세션 준비 중에도** 보낼 수 있다(큐에 대기 → 준비되는 즉시 두 번째 청크부터 발화). `말하기`는 즉시 응답하고 TTS는 백그라운드에서 **한 번의 `say` 호출**로 만든다 — `say -v "Yuna (Premium)"`는 호출당 ~4 s의 기동 오버헤드가 있어 문장별로 나누면 4문장에 20 s가 걸렸고, 문단 통째로는 ~2–3 s. Pro 워커는 기동 시 워밍업을 해 첫 청크도 0.7 s(전에는 1.9 s). 2026-09-14 수정 전에는 Pro 감독→워커 FIFO에 문장 PCM을 base64 한 줄로 넘겨 20 s 문장이 ~7 s 걸렸고(64 KB 파이프를 루프당 한 번 읽음), 그동안 무음 청크 7–8개가 먼저 나갔다 → PCM은 파일로 넘기고 FIFO는 한 번에 비운다.
- 라이브 중에는 해당 모델의 컨테이너(`max_containers=1`)를 세션이 점유하므로(Lite면 일반 렌더 잡이 대기) 세션은 한 번에 하나.
- 서버: `POST /api/live {avatar, model: lite|pro}`, `POST /api/live/{sid}/say {text}`(문장 PCM을 ≤800 KB 조각 + `final` 표시로 전송; 청크 크기 0.96/1.12 s는 컨테이너가 자름), `POST /api/live/{sid}/stop`, `GET /api/live[/{sid}]`, `/hls/live/{sid}/…`, `/videos/live/{sid}.mp4`.
- 지연을 더 줄이려면: 큐 대신 WebSocket(왕복 −1.4 s), 세그먼트 대신 CMAF 조각(−1 s), Pro 실시간은 2×H100 경로로 교체.

## Pro 최종 렌더 (카드의 버튼)

완료된 카드에서 **"Pro 최종 렌더"**를 누르면 같은 `speech.wav`·아바타·시드를 `Renderer(model_type="pro")`에 보내 `jobs/<id>/video_pro.mp4`를 만들고 카드 아래에 PRO 영상으로 추가한다.

- Pro는 Wan2.1 VAE(잠재 64×64)라 화질·표정이 크게 낫지만 L4에서 청크(28프레임=1.12 s)당 **~8.6 s** → 오디오 길이의 약 8배 + 콜드 스타트 1–2분. 버튼에 예상 시간이 표시된다. 스트리밍 재생은 불가하므로 완성 후 재생.
- `model_type`은 `modal.parameter` — Pro는 **별도 컨테이너 풀**(Lite 스트리밍과 동시에 돌 수 있고, 마지막 사용 10분 뒤 자동 종료). 준비 플래그도 `ready:lite` / `ready:pro`로 나뉜다.
- 스튜디오는 Pro 전용 워커 스레드로 처리하므로 Lite 잡 대기열을 막지 않는다. 진행 줄은 큐 파티션 `<job>:pro`.
- 서버: `POST /api/jobs/{id}/pro`, `GET /videos/pro/{id}.mp4`, `POST /api/jobs/{id}/reveal?which=pro`.

## 영상 길이와 꼬리 무음

렌더러는 오디오를 **음성 끝 + 0.5 s**(`VIDEO_TAIL_S`)를 영상이 덮을 때까지 무음으로 패딩한다. 청크 격자가 0.96 s라 실제 꼬리는 0.5–1.46 s. 상류 `once` 코드를 그대로 쓰면 영상이 패딩된 오디오보다 늘 0.96 s 짧아서, 정렬에 따라 마지막 음절이 최대 0.96 s 잘리고 입과 소리가 도중에 함께 끊겼다(2026-09-11 실측: 음성 끝 3.40 s / 영상 3.24 s 등).

## 음성 파일 입력

멘트를 타이핑하는 대신 **음성 파일을 그대로** 쓸 수 있다(TTS를 거치지 않음).

- 클립: 입력란 아래 **"음성 파일로 만들기"** → 카드에 `음성 파일` 배지와 파일명이 표시된다. 라이브: 세션 패널의 **"음성 파일"** 버튼 → 그 음성이 다음 청크부터 재생된다.
- 어떤 형식이든 ffmpeg로 **16 kHz mono PCM**(FlashHead wav2vec2 입력 형식)으로 변환한다 — mp3/m4a/wav/aac, 44.1 kHz·스테레오, 동영상 파일의 오디오 트랙(`-vn`)도 가능. 업로드 시 `ffprobe`로 즉시 검증해 잘못된 파일은 카드가 아니라 요청에서 거절한다.
- 한도: 200 MB / 900초(`AUDIO_MAX_BYTES`, `AUDIO_MAX_SECONDS`). 원본은 `jobs/<id>/upload.*`, 변환본은 `speech.wav`로 남는다.
- 서버: `POST /api/jobs/audio` (multipart: `file`, `avatar`), `POST /api/live/{sid}/say_audio` (multipart: `file`).

## 아바타

- `avatars/` 폴더의 이미지(png/jpg/webp)가 그대로 선택지다. 파일 이름(확장자 제외)이 id이자 표시 이름. 기본값 `newscaster`.
- 페이지의 "+ 추가" 타일로 업로드하면 EXIF 회전을 적용해 PNG로 다시 저장한다(긴 변 2048 px 상한, 짧은 변 256 px 미만은 거절, 같은 이름은 `-2`, `-3`…). 지우려면 파일을 삭제하면 된다.
- 렌더는 참조 이미지를 얼굴 기준으로 자른다(`use_face_crop=True`, mediapipe). 정면에 가깝고 얼굴이 크게 나온 상반신 사진이 잘 되고, 얼굴을 못 찾으면 이미지 전체를 512²로 센터크롭한다.
- 마지막 선택은 브라우저 `localStorage`에 남고, 잡마다 어떤 아바타를 썼는지 `job.json`에 기록된다.

## 예열 스위치 (헤더 우측)

| 상태 표시 | 의미 |
|---|---|
| GPU 꺼짐 (과금 없음) | 컨테이너 없음. 다음 잡은 기동+로딩 **85–125 s**를 먼저 낸다 |
| GPU 시작·모델 로딩 중… | 컨테이너는 떴지만 `enter()` 진행 중. 이때 보낸 잡은 준비될 때까지 대기 |
| GPU 준비됨 · 상주 중 (과금) | 스위치 ON. **L4 $0.799/hr**, 끄는 걸 잊으면 하루 ~$19 |
| GPU 준비됨 · 유휴 시 자동 종료 | 스위치 OFF, 마지막 잡 후 10분 뒤 자동 종료 |

- 스위치는 `Renderer().update_autoscaler(min_containers=1|0)`를 부른다. **`modal deploy`가 이 값을 초기화**하므로 스튜디오가 `warm.json`을 진실로 삼고 기동 시 다시 적용한다.
- "준비됨"은 컨테이너에서 `enter()`가 끝날 때 세우는 `modal.Dict("flashhead-state")["ready"]` 플래그로 판단한다(`modal container list`는 로딩 중도 1로 보임).

## 시간 감 (2026-09-11 실측)

- 예열된 상태: 멘트 11.6 s → **19.6 s**에 완성(TTS ~2 s + 렌더 11.9 s + 전송). 렌더는 청크(0.96 s 분량)당 0.8 s, 즉 오디오 길이와 비슷.
- 꺼진 상태: 위에 컨테이너 기동+로딩 85–125 s가 붙는다.
- 이전(잡마다 `modal run` 서브프로세스, compile off): 2.6 s 클립 71 s. 더 이전(compile on): 7.8 s 멘트 587 s.
- 비용: 잡당 수 센트. 예열은 시간당 $0.80.

## 파일

- `server.py` — FastAPI. `/api/jobs` (POST `{text, avatar}`/GET), `/api/jobs/{id}`, `POST /api/jobs/{id}/reveal`(Finder), `/hls/{id}/{init.mp4|seg_NNN.m4s|index.m3u8}`, `/videos/{id}.mp4`, `/api/avatars` (GET 목록 / POST multipart 업로드), `/avatars/<file>` 썸네일, `/api/warm` (GET/POST `{on}`), `/api/config`
- `index.html` — 단일 페이지. 아바타 타일 선택·업로드, 2 s(작업 중)/6 s 폴링, 카드는 **제자리 갱신**(비디오 엘리먼트는 한 번만 만들어 재생이 끊기지 않게), 청크 진행바, 로그 콘솔, 예열 스위치
- `avatars/` — 아바타 라이브러리 (`newscaster.png`, `woman.png` + 업로드분)
- `jobs/<id>/` — `text.txt`(TTS일 때) 또는 `upload.*`(업로드일 때), `speech.wav`, `hls/`(init + 세그먼트 + 플레이리스트), **`video.mp4`**(리먹스 결과), `video_pro.mp4`(Pro 최종본, 요청 시), `job.json`(아바타 id 포함; 완료 잡은 재시작 후에도 복원)
- `warm.json` — 예열 스위치의 마지막 값
- `studio.log` — uvicorn 로그

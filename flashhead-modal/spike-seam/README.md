# 스파이크: 대기 루프 → 실시간 생성 전환 이음새

**질문** — 라이브 세션에서 무음 구간을 미리 렌더한 대기 루프 재생으로 바꾸고,
아바타가 말할 때만 생성을 붙일 수 있는가? 그러려면 루프에서 생성으로 넘어가는
순간이 매끄러워야 한다.

**방법** — FlashHead는 청크마다 `latent_motion_frames`(직전 9프레임의 VAE 잠재값)를
조건으로 이어 그린다. 그 자리에 대기 루프의 마지막 프레임을 주입하고, 같은 시드·
같은 오디오로 24초(25청크)를 생성해 세 조건을 비교했다.

| 조건 | 주입 경로 | 손실 |
|---|---|---|
| **C** 대조군 | 파이프라인이 들고 있던 float 잠재값 (GPU 밖으로 나간 적 없음) | 없음 |
| **A** | 메모리의 uint8 프레임을 다시 인코딩 | 양자화 |
| **B** | **저장된 mp4에서 디코딩한 프레임**을 다시 인코딩 (실제 운영 조건) | 양자화 + h264 |

## 결과 (L4, Lite, newscaster, 2026-09-17)

기준값: h264 왕복으로 프레임 자체가 입는 손실 **3.05 MAD**, 자연스러운 프레임 간
변화 1.73(무음) / 3.05(발화).

| 조건 | 경계 점프 | 발화 중 프레임 간 | 대조군 대비 발산 |
|---|---|---|---|
| C 대조군 | 4.38 | 3.05 | 0 |
| A uint8 | 4.34 | 3.04 | 1.43 |
| **B h264 파일** | **4.60** (+5%) | 3.06 | 1.82 |

**오차는 누적되지 않고 스스로 잦아든다.** B의 청크별 발산: 4.1 → 3.5 → 2.3 → 2.2 →
… → 1.3. 8청크(약 8초) 만에 A와 같은 바닥값에 도달하고 이후 평평하다. 색도
안정적이다(루프 마지막 RGB 70.6/81.2/119.0 → 생성 마지막 70.2/81.3/118.8).

육안으로도 이음새가 보이지 않는다 — `strip_B_h264_file.png`(대기 3프레임 + 생성 5프레임).

## 판정

**통과.** 대기 루프를 평범한 mp4로 저장해 두고 발화 시점에 생성을 이어 붙여도
보통의 청크 경계와 구분되지 않는다. 무손실 보관 같은 절충안이 필요 없다.

따라서 "GPU = 동시 세션 수"를 **"GPU = 동시에 말하는 세션 수 + 여유분"** 으로
바꾸는 구조가 모델 쪽에서는 성립한다. 남은 것은 인프라 쪽이다:
세션 상태(잠재값 128 KB + 오디오 창 512 KB) 이동, 1초 내 GPU 배정 스케줄러,
그리고 실제 면접에서의 아바타 발화 비중 측정.

재현: `modal run app.py::seam`

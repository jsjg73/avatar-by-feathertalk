# 사실 시트 — FlashHead on Modal 실시간 아바타 면접 (역할극 공통 근거)

작성 2026-09-15. 이 문서는 역할극에 참여하는 모든 에이전트의 **유일한 사실 근거**다.

## 0. 규칙 (모든 에이전트 필독)

- 여기 적힌 수치만 "실측"으로 인용한다. 그 외 수치는 반드시 `[추정]` 또는 `[모름/확인 필요]`로 표기한다.
- 제3자 서비스(HeyGen, D-ID, Tavus 등)의 가격·성능을 **지어내지 않는다**. 이름을 거론하는 것은 가능하나 수치는 `[확인 필요]`.
- 법·규제는 결론을 단정하지 않는다. "법무 검토 필요 항목"으로 제시한다.
- 출력은 한국어. 기술 용어는 원어 그대로 써도 된다.
- 기획자에게 전달될 문서의 재료다. 문장은 짧고 구체적으로.

## 2. 팀 상황

- 개발팀 보유 역량: 백엔드(Python/API), 프론트엔드/웹, DevOps/클라우드 운영.
- **없는 역량**: ML/모델 서빙(PyTorch·CUDA·모델 최적화), GPU 인프라 대여·스트리밍 서비스 운영 경험. 팀 내 누구도 GPU 스트리밍 서비스를 운영해본 적 없음.
- 담당자(이 문서의 의뢰인)는 기획자에게 가능성과 위험을 정확하고 명료하게 전달해야 하는 입장.

## 3. PoC에서 실제로 만든 것 (2026-09-10 ~ 09-15)

구조:
- Mac에서 스튜디오 서버(FastAPI)가 돌고, 텍스트를 macOS `say`로 음성(PCM)으로 만든 뒤 Modal의 상주 GPU 컨테이너로 보낸다.
- Modal 쪽 `Renderer` 클래스(L4 24GB, `max_containers=1`, 유휴 600 s 후 종료)가 FlashHead Lite로 영상을 생성하고, 컨테이너 안 ffmpeg가 HLS fMP4 세그먼트(청크 0.96 s = 1세그먼트)를 만들어 `modal.Queue`로 Mac에 넘긴다. Mac이 세그먼트를 파일로 받아 hls.js 플레이어에 서빙한다.
- 라이브 세션(`Renderer.live`): 벽시계에 맞춰 0.96 s 청크를 계속 생성. 음성이 오면 다음 슬롯부터 말하고, 없으면 무음 청크(입 다물고 미세 움직임)로 대기. 세션 종료 시 녹화 mp4 생성.
- Pro 라이브(`LivePro`): 2×H100(도쿄 `jp` 리전) 컨테이너 안에 `torchrun` 2랭크 워커 상주, xfuser 시퀀스 병렬. 청크 1.12 s.
- **한 컨테이너 = 한 세션.** GPU는 세션이 열려 있는 동안 아바타가 말하든 대기하든 계속 점유·과금.
- 담당자 표현: "1개 세션을 시작해서 3초 이내에 아바타가 발화를 시작하는 PoC를 마쳤다." README 실측 정의는 §4 참조. **"3초"가 어느 구간인지 기획자용 정의를 반드시 명시해야 한다.**

## 4. 실측 수치 (모두 실측, 출처: README·`modal billing report`)

### 4-1. 지연 (Lite 라이브, L4, 예열된 컨테이너, 2026-09-14)

| 구간 | 실측 |
|---|---|
| "말하기" 클릭 → 컨테이너가 해당 음성 청크를 **생성**한 로그 도착 | **3~4 s** (TTS ~1 s + Queue 0.7 s + 슬롯 대기 ≤0.96 s + 생성 0.8 s + 로그 전달) |
| "말하기" 클릭 → **화면에 보임** | **6~7 s** (위 + 세그먼트 닫힘 0.96 s + 전송 0.7 s + 플레이어 버퍼 1.5 s) |
| 청크 생성 시간 | 0.80~0.85 s / 0.96 s 청크 (실시간 대비 1.18×, 여유 15~20%) |
| 스케줄 지연 | 0.03~0.04 s로 고정 (벽시계 동기 유지됨) |

주의: 이 지연에는 **STT와 LLM이 포함되지 않는다** (PoC는 텍스트 입력). 지원자 발화 끝 → STT → LLM 첫 토큰 → TTS 첫 패킷이 앞에 더 붙는다.

## 5. 데모용으로만 있는 부분 (실서비스에서 전부 교체 필요)

| 구성요소 | PoC 상태 | 실서비스 요구 |
|---|---|---|
| TTS | macOS `say -v "Yuna (Premium)"`. Mac 전용, 호출당 ~4 s 기동 오버헤드, 스트리밍 아님 | 클라우드/자체 **스트리밍** TTS. 한국어 품질·첫 패킷 지연·동시 1000 스트림 계약 |
| STT | 스텁(빈 문자열 반환) | 한국어 실시간 STT, 발화 종료 감지(VAD/endpointing) |
| LLM | 에코(입력 그대로 반환) | 면접관 LLM: 질문 생성·꼬리질문·평가. 스트리밍 응답 필수 |
| 전송 | HLS 세그먼트 + `modal.Queue` → Mac 서버 → hls.js | WebRTC(또는 최소 WebSocket+CMAF). 수천 클라이언트 동시 접속 구조 |
| 세션 관리 | 스튜디오 서버 1대, 세션 1개 | 스케줄링, 대기열, 재접속, 장애 복구, 감사 로그 |
| 오디오 입력 | 없음 (텍스트 입력) | 브라우저 마이크 캡처 → 서버 |

이전 측정(OpenTalking 프레임워크, RTX 4090, 2026-09-10): 한 턴 3606 ms 중 **TTS 첫 패킷(TTFA) 1507 ms**, 아바타 렌더 589 ms. **병목은 GPU 렌더가 아니라 TTS/LLM 쪽**이었다. GPU를 올려도 체감 지연은 거의 줄지 않는다.

## 6. 용량·리전 사실 (Modal, 2026-09-14~15 실측)

| 지정 | 실제 위치 | 실측 |
|---|---|---|
| `ap-northeast` | GCP asia-northeast3 = **서울** | L4 **3대 동시** ~26 s에 배정. **6대 동시 요청은 한 번 240 s 내 미배정** |
| `jp` | asia-northeast1 = 도쿄 | L4 90 s, H100 13 s. H100:2 수 초 |
| `ap` | 싱가포르/서울/도쿄 중 가용한 곳 | 19~125 s (순간 용량에 따라) |
| 미지정 | us-central1 | 12 s. 한국까지 RTT 150 ms+ |
| H200:2 | jp / ap-northeast | **240 s 내 미배정** (H200 용량은 미국/유럽) |
| 지리 지연 | 서울 ~5~15 ms, 도쿄 ~35~45 ms, 싱가포르 ~70~90 ms (한국 사용자 기준) |

- 용량은 순간마다 변한다. 예약형 세션이면 T−3~5분에 `ap-northeast → ap → any` 순으로 시도하는 배치 정책을 권고했다.
- **Modal 워크스페이스의 동시 GPU 한도(쿼터)는 확인하지 않았다.** `[모름/확인 필요]` 1000 L4 또는 2000 H100 동시 확보는 셀프서브 요금제 범위를 명백히 넘는다 → Modal 영업/엔터프라이즈 계약 필요 여부 확인.
- Blackwell(B200, RTX PRO 6000)은 현재 이미지(cu124, torch 2.6)에서 커널 없음 → cu128 재빌드 필요.

## 7. Modal 특성과 함정 (실제로 겪은 것)

- `update_autoscaler`(예열 설정)는 **`modal deploy`마다 초기화**된다. 배포하면 예열이 꺼진다.
- `modal app stop` 또는 콘솔 Stop → 모든 호출이 `ConflictError`로 실패. 재배포해야 살아남.
- `modal container list`는 로딩 중 컨테이너도 보여줌. 진짜 준비 여부는 자체 플래그(Dict + 20 s 심장박동)로 판단해야 했다. 교체된 컨테이너의 옛 플래그가 남아 '준비됨'으로 오판한 사례 있음.
- Modal **제너레이터(`remote_gen`)는 출력이 5~20 s 늦게 묶여 도착** → 지연 민감 경로에 사용 불가.
- `modal.Queue` 항목 하나에 왕복 ~0.5~0.8 s, 항목 ≤1 MiB. 청크당 항목을 하나로 묶어야 뒤처지지 않았다.
- 의존성 드리프트: `xfuser>=0.4.3`이 0.6.0으로 풀려 멀티 GPU 경로가 전부 ImportError. `xfuser==0.4.5` 고정으로 해결. torch.compile은 멀티 GPU(USP)에서 오히려 느리고 흔들림(0.71~1.99 s 지터, 첫 청크 310 s 컴파일).
- 배포된 메서드의 stdout은 호출자에게 오지 않음 → 진행 로그를 Queue로 따로 보내야 했다.
- 로그 재구성에는 `modal app logs --since --timestamps --show-container-id`가 필요.

## 8. 품질에 대해 아는 것 / 모르는 것

아는 것:
- Lite는 입술이 뭉개져 보인다. Pro는 뚜렷하다 (§4-5).
- 얼굴이 크게 나온 정면 상반신 사진이 잘 된다. 512×512 출력.
- 무음 시 대기 동작(입 다물고 미세 움직임) 있음.

모르는 것 `[모름/확인 필요]`:
- **FlashHead의 한국어 음소 정확도.** 다른 모델(wav2lip, QuickTalk, JoyVASA) 측정에서는 입 벌림은 되지만 **입술 오므림(우)은 거의 재현되지 않았다.** FlashHead는 미측정.
- 30~60분 세션에서의 드리프트(얼굴 변형·색 변화·정체성 유지).
- 여러 아바타(성별·연령·인종)에 걸친 품질 편차.
- 지원자가 말하는 동안 길게 대기할 때의 자연스러움(수 분 무음).
- 아바타가 말을 끊거나(barge-in) 지원자가 끼어들 때의 처리 — PoC에 없음.
- 한 GPU에서 여러 세션 다중화 가능성: FlashHead 논문은 RTX 4090에서 96 fps·3 스트림을 주장. L4는 메모리 대역폭이 4090의 약 30%(300 vs 1008 GB/s)이고 실측 여유가 15~20%라 **L4 1대 = 1세션**이 현재 사실. 다중화는 설계상 가능성일 뿐 미검증.

## 9. 라이선스 사실

- FlashHead 1.3B: **Apache-2.0** (상용 가능). Wan2.1 VAE: Apache-2.0. mediapipe(얼굴 크롭): Apache-2.0. wav2vec2 오디오 인코더: 사용 중인 체크포인트의 라이선스 `[확인 필요]`.
- 배제한 엔진과 이유: wav2lip(LICENSE 파일 없음 + 비상업 명시), QuickTalk(InsightFace `buffalo_l` 비상업 연구 전용 의존), MuseTalk·Hallo·JoyVASA(InsightFace 공유 문제), HunyuanVideo-Avatar(**라이선스가 대한민국을 명시적으로 배제**).
- 아바타 얼굴 이미지 자체의 권리(초상권·퍼블리시티권·촬영 동의)는 별도 문제. 실제 인물 사진을 쓰면 그 사람의 동의가 필요.

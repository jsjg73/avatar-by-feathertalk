## A. 질문 44개 답변

### 1. 지원자가 겪는 경험

#### Q1-1. "3초"는 어느 구간인가
- **한 줄 답**: 지원자 화면에 아바타 입이 움직이기까지는 **6~7초**(전제: 텍스트 입력, Lite, 예열된 L4, STT·LLM 없음)이고, "3초"는 내부 생성 완료까지의 개발자용 숫자다 — 외부에는 어느 쪽도 "응답 속도"로 쓰면 안 된다.
- **확신도**: 실측(2026-09-14, Lite 라이브, L4, 예열 컨테이너). 단, 시작점이 "말하기 클릭"이지 "지원자 발화 끝"이 아니다.
- **상세**: §4-1의 두 줄이 서로 다른 구간이다. "말하기 클릭 → 컨테이너가 음성 청크를 생성한 로그 도착"이 3~4초이고, 여기에 세그먼트 닫힘 0.96초 + 전송 0.7초 + 플레이어 버퍼 1.5초가 더해져 "화면에 보임"이 6~7초다. 지원자가 느끼는 것은 당연히 후자다. 그리고 두 숫자 모두 시작점이 **텍스트를 넣은 순간**이다. 지원자가 말을 끝낸 순간부터 재면 STT(음성→글자)와 LLM(답변 생성)이 앞에 더 붙는다(Q1-2). 구간 분해는 아래 표.

| 구간 | 실측 | 비고 |
|---|---|---|
| 지원자 발화 끝 → STT 최종 텍스트 | 없음 | PoC에 STT 없음(스텁) |
| STT → LLM 첫 문장 | 없음 | PoC LLM은 에코 |
| 텍스트 → TTS 음성 | ~1 s | macOS `say`(데모용) |
| Queue 왕복 | 0.7 s | Modal 큐 특성 §7 |
| 슬롯 대기 | ≤0.96 s | 0.96 s 청크 단위로 동작 |
| 청크 생성 | 0.8 s | L4 Lite |
| (여기까지 "3~4초") | | |
| 세그먼트 닫힘 | 0.96 s | HLS 구조 |
| 전송 | 0.7 s | Queue → Mac 서버 |
| 플레이어 버퍼 | 1.5 s | hls.js |
| (여기까지 "6~7초") | | |

- **기획자가 하면 안 되는 말**: "지원자가 말을 끝내면 3초 뒤에 아바타가 대답합니다."

#### Q1-2. STT·LLM을 붙이면 총 몇 초인가
- **한 줄 답**: 지금 구조 그대로 STT·LLM을 붙이면 지원자가 말을 끝내고 아바타 입이 열리기까지 **[추정] 8~12초**(전제: 상용 스트리밍 STT/LLM, 현재 HLS 전송 유지)이고, §11의 전송·TTS 개선을 전부 구현해야 **[추정] 3~5초**대로 내려간다.
- **확신도**: 부분 실측 + 추정. 실측인 것: 텍스트 이후 화면까지 6~7 s(§4-1), 다른 프레임워크에서 TTS 첫 패킷 1.5 s(§5, 2026-09-10, RTX 4090). 추정인 것: STT·LLM 구간(벤더 미정). 모름: 실제 합산치(확인 방법: 벤더 API 붙여 10턴 실측, 소요 2~3주, 비용 벤더 체험 크레딧 + GPU 수 달러).
- **상세**: 단계별로 나누면 (1) 발화 종료 감지+STT 최종 텍스트 [추정 0.5~1.5 s, 전제: 스트리밍 STT], (2) LLM 첫 문장까지 [추정 0.5~2 s, 전제: 스트리밍 LLM], (3) TTS 첫 패킷 1.5 s [실측, 단 다른 TTS·다른 장비], (4) 큐·슬롯·생성·세그먼트·전송·버퍼 ≈ 5~6 s [실측 6~7 s에서 TTS ~1 s를 뺀 값]. 합하면 8~12 s. §5의 결론이 중요하다: 2026-09-10 측정에서 한 턴 3.6 s 중 TTS 첫 패킷이 1.5 s, 렌더는 0.6 s였다. **병목은 GPU가 아니라 TTS/LLM과 전송 구조**다. §11의 WebSocket 직접 전송(−1.4 s), CMAF(−1 s), WebRTC(버퍼 1.5 s 제거), 스트리밍 TTS를 모두 하면 3~5 s대가 목표치인데 전부 미구현이다.
- **기획자가 하면 안 되는 말**: "STT·LLM은 요즘 다 빠르니까 1초 정도만 더 붙을 겁니다."

#### Q1-3. PoC에서 실제 "대화"를 한 번이라도 했나
- **한 줄 답**: **아니오, 0회다** — 마이크 입력·STT·LLM이 전부 없거나 가짜(스텁·에코)였고, 첫 마이크→대답 시연은 **[추정] 3~4주 뒤**(전제: STT/LLM/TTS 벤더 체험 계정을 1주 안에 확보, 데모 품질 기준)에 가능하다.
- **확신도**: 실측(§5: 오디오 입력 없음, STT 스텁, LLM 에코). 날짜는 추정.
- **상세**: PoC는 "텍스트를 넣으면 아바타가 그 문장을 말한다"까지다(§3). 대화 루프의 앞 절반(듣기·이해·답 만들기)은 손대지 않았다. 마이크 캡처와 벤더 API 연동은 백엔드·프론트 역량으로 가능한 일이라 시연 수준은 3~4주면 만들 수 있다고 본다. 단, 그 시연은 벤더 API에 지원자 음성을 보내는 구조이므로 데이터 흐름 문제(Q8-4)가 그 순간부터 생긴다. 경영진이 "대화형 PoC 완료"로 알고 있다면 이번 주에 "발화 렌더 PoC 완료, 대화 루프는 미착수"로 고쳐야 한다.
- **기획자가 하면 안 되는 말**: "대화형 면접 PoC가 끝났습니다."

#### Q1-4. 말이 겹치면
- **한 줄 답**: 지금은 지원자가 끼어들어도 **아바타가 하던 말을 끝까지 한다**(마이크 자체가 없으니 끼어듦을 감지할 방법도 없다). 끼어듦 처리(barge-in)는 마이크 루프가 생긴 뒤 **[추정] 2~4주** 추가 작업이다.
- **확신도**: 현재 동작은 실측(§3 라이브 세션 구조, §8 barge-in 없음). 기간은 추정(전제: Q1-3의 마이크 루프 완성 후, 백엔드 인력으로).
- **상세**: 라이브 세션은 0.96 s 청크를 벽시계에 맞춰 계속 만든다(§3). 음성이 큐에 들어 있으면 그것을 소진할 때까지 말한다. 끼어듦을 처리하려면 (1) 브라우저에서 지원자 음성 활동 감지(VAD), (2) 서버가 남은 TTS 음성과 렌더 큐를 즉시 버리고 무음 청크로 전환, (3) LLM 응답 스트림 취소가 필요하다. 반대 경우(지원자가 말하는 중에 아바타가 시작)는 발화 종료 감지(endpointing) 품질 문제로, STT 벤더 기능에 크게 의존한다. 면접 특성상 "아바타는 끼어들지 않는다"는 규칙으로 단순화할 수 있다 — 지원자 발화 중에는 절대 응답을 시작하지 않는 것이다.
- **기획자가 하면 안 되는 말**: "사람처럼 자연스럽게 말을 주고받습니다."

#### Q1-5. 긴 침묵과 끊김
- **한 줄 답**: 침묵 중 아바타는 **입을 다물고 미세하게 움직이는 대기 영상**을 계속 내보내고(그동안 GPU는 계속 과금), 수 분 침묵의 자연스러움과 끊김 빈도는 **측정한 적 없다**(확인: 3분 무음 포함 세션 녹화 1회, 소요 1일, 비용 $5 미만).
- **확신도**: 대기 동작 존재는 실측(§3, §8). 스케줄 지연 0.03~0.04 s로 안정된 것은 실측(§4-1, 수 분 단위). 수 분 무음 자연스러움은 모름(§8). 끊김 빈도는 모름.
- **상세**: 무음일 때 서버는 무음 청크를 생성해 영상이 끊기지 않게 한다(§3). 벽시계 동기가 유지되므로(§4-1) 원리상 버퍼링은 나지 않아야 하지만, 이는 짧은 세션에서 관찰한 것이다. 30분 세션에서 hls.js 버퍼가 어떻게 되는지, 네트워크 흔들림에서 어떻게 보이는지는 데이터가 없다. 요청한 "2~3분 무음 포함 시연 영상"은 하루면 만들 수 있다. 데모 리스크 관점에서는 이 영상을 먼저 만들고 보여드리겠다.
- **기획자가 하면 안 되는 말**: "지원자가 생각하는 동안에는 GPU 비용이 안 나갑니다."

### 2. 화질·자연스러움

#### Q2-1. Lite로 팔 수 있는 화질인가
- **한 줄 답**: Lite는 "아바타가 말한다"는 것은 전달되지만 **입술을 보면 뭉개짐이 보이고 표정이 거의 없다**(실측 비교, 입 영역 선명도 Pro의 1/1.8) — 영업 자료에는 어느 화질인지 **명시하고** 넣어야 하며, 1000 세션에서 현실적인 후보는 Lite다.
- **확신도**: 실측(§4-5, 2026-09-14, 동일 아바타·음성·시드). "HR이 어색하다고 느낄지"는 개발팀의 육안 평가(추정)이고 사용자 평가는 없다(확인: HR 담당자 5~10명 블라인드 비교, 소요 1주, 비용 녹화 수 달러).
- **상세**: §4-5에서 Lite는 VAE 잠재 16×16, 입 영역 라플라시안 분산 71, 육안으로 입술 뭉개짐·표정 적음. Pro는 64×64, 128(×1.8), 치아·입술 윤곽·혀·눈 깜빡임·미소가 보인다. 개발팀의 솔직한 한 줄: **"Lite는 화상회의 저화질 정도, Pro는 팔 수 있는 화질. 단 Pro는 세션당 $7.90/hr에 2×H100이 필요해 1000 세션은 H100 2000장이다(§10)."** 그래서 자료는 Pro로 찍고 서비스는 Lite로 나가는 상황이 생기기 쉽다(Q10-3). 나란히 비교 영상은 이미 같은 조건으로 만들 수 있으니 이번 주에 제공하겠다.
- **기획자가 하면 안 되는 말**: (Pro 영상을 보여주며) "이 화질로 1000명 동시에 됩니다."

#### Q2-2. 한국어 입모양
- **한 줄 답**: FlashHead의 한국어 입모양(특히 '우'·'오' 같은 입술 오므림)은 **아직 측정하지 않았다** — 확인은 **2~3일**(예열 컨테이너에서 테스트 문장 렌더, 비용 $5 미만)이면 되고, 안 될 경우 우리 팀 역량으로는 모델을 고칠 수 없어 대안은 "그대로 받아들이기 / Pro 재확인 / 구매"다.
- **확신도**: 모름(§8). 다른 모델(wav2lip·QuickTalk·JoyVASA)에서 입술 오므림이 거의 재현되지 않은 것은 실측이나 FlashHead에는 적용 불가.
- **상세**: 확인 방법: 양순음·원순모음이 몰린 문장("우유를 오후에 마셨습니다", "부모님과 함께 보문호를 보았습니다" 류)을 Lite·Pro로 렌더해 프레임을 캡처하고, 입 벌림/오므림/다물림 3종을 사람이 판정한다. 정량화는 mediapipe 입 랜드마크로 가로세로 비율을 뽑을 수 있다(팀 역량 안). 결과가 나쁘면: 모델 미세조정(fine-tune)은 ML 엔지니어가 없어 지금 팀으로는 못 한다. 그 경우 선택은 (a) "입이 움직이는 아바타"로 기대치를 낮춰 판다, (b) 상용 API의 한국어 성능을 비교한다(§13-1, [확인 필요]), (c) 음성 우선 상품으로 간다(§13-4). 고객이 "입모양이 이상하다"고 하면 답은 지금 없다 — 그래서 측정을 먼저 한다.
- **기획자가 하면 안 되는 말**: "한국어 발음에 맞춰 입모양이 정확히 움직입니다."

#### Q2-3. 30분~1시간 연속 세션
- **한 줄 답**: **1시간 연속으로 돌려본 적 없다**(PoC 세션은 분 단위) — 테스트는 **1~2일**, 비용 Lite 1시간 ≈ $0.80 + Pro 1시간 ≈ $7.90이면 되고, 결과 전에는 "30분 면접 가능"을 약속할 수 없다.
- **확신도**: 모름(§8: 30~60분 드리프트 미측정). 테스트 비용은 §4-4 단가 산술.
- **상세**: 이런 모델은 앞 프레임을 참조해 다음 프레임을 만들기 때문에, 오래 돌리면 얼굴이 조금씩 변하거나 색이 틀어질 가능성이 있다(일반적 위험이며 FlashHead에서 실제 그런지는 모른다). 확인 방법: 60분 라이브 세션을 말하기·침묵 반복으로 돌리고 0·15·30·45·60분 캡처를 나란히 비교, 녹화 mp4로 육안 검토. 이 테스트는 지금 팀이 바로 할 수 있다. 결과가 나쁘면 "N분마다 참조 이미지로 재초기화"라는 우회가 있을 수 있지만 그 구현 가능성은 [추정]이다.
- **기획자가 하면 안 되는 말**: "1시간 면접도 문제없이 됩니다."

#### Q2-4. 화면 크기와 아바타 다양성
- **한 줄 답**: 출력은 **512×512 고정**이라 노트북 전체화면에서는 확대되어 부드럽게(흐릿하게) 보일 것이고 [추정], 아바타 성별·연령별 품질 편차는 **미측정**(확인: 사진 3~4종 렌더 비교, 1~2일, $5 미만)이다.
- **확신도**: 해상도는 실측(§4-5). 전체화면 인상은 추정(512를 1080p 세로에 맞추면 2배 이상 확대). 다양성은 모름(§8).

#### Q8-4. STT·LLM·TTS 외부 API와 제3자 전달
- **한 줄 답**: **예, 외부 API를 쓰면 지원자 음성·답변 텍스트가 그 벤더로 간다** — 후보 벤더의 처리 위치(미국인지, 국내·일본 리전이 있는지)는 전부 [확인 필요]이고, 자체 운영(오픈소스 STT/LLM/TTS를 우리 GPU에)은 ML 서빙 인력이 있어야 가능하다.
- **확신도**: 구조는 사실. 벤더별 위치·보관 정책 [확인 필요](조사: 후보 3개씩, 2주, 담당 개발팀 리드+기획).
- **상세**:

| 구성 | 외부 API 시 이동 데이터 | 위치 | 자체 운영 대안 |
|---|---|---|---|
| STT | 지원자 음성 전체 | 벤더별 [확인 필요]. 국내 벤더 후보도 조사 | 오픈소스 음성인식 모델을 GPU에 올림 — 한국어 품질·지연 [모름], ML 인력 필요 |
| LLM | 답변 텍스트·질문·평가 | 벤더별 [확인 필요]. 국내 리전 제공 여부 조사 | 오픈 모델 자체 서빙 — 면접 품질 [모름], GPU 추가 비용 |
| TTS | 면접관 대사 텍스트(지원자 정보 최소) | 벤더별 [확인 필요] | 오픈소스 TTS — 한국어 품질·첫 패킷 지연 [모름] |

지원자 개인정보 노출을 줄이는 설계: 음성은 STT 외에는 보내지 않기, LLM에 지원자 실명·식별정보를 넣지 않기(가명 처리), 벤더의 "학습에 미사용·보관 0일" 옵션 계약 [확인 필요]. 고지 의무 여부는 법무 판단이며, 개발팀은 "어느 데이터가 어디로 가는지" 표를 확정해 주는 역할이다.
- **기획자가 하면 안 되는 말**: "지원자 데이터는 우리 서버 안에서만 처리됩니다."

#### Q8-5. AI 고지·표시와 아바타 얼굴 권리
- **한 줄 답**: 화면 고지·영상 표시는 **쉽다**(브라우저 오버레이 또는 ffmpeg 워터마크, [추정] 1~3일) — 아바타 얼굴은 **PoC 이미지의 상용 사용 권리를 확인하지 않았고**, 실제 인사담당자 얼굴은 기술적으로 가능하지만 본인 동의·계약 조항·퇴사 시 처리가 필요하다(법무).
- **확신도**: 구현 난이도는 추정. 이미지 권리는 [확인 필요](§9).
- **상세**: 표시 방식 후보: (1) 면접 시작 전 동의 화면에 "AI 면접관과 대화 중" 고지, (2) 영상 위 상시 배지(브라우저 오버레이 — 가장 쉽고 영상 품질 영향 없음), (3) 영상 자체에 워터마크(컨테이너 ffmpeg 단계 — 녹화본에도 남음), (4) 음성 시작 시 안내 멘트. 법무가 어느 방식이 요건을 충족하는지 정하면 바로 구현한다. 아바타 이미지: 실서비스는 권리가 명확한 이미지(계약된 모델 촬영 또는 라이선스가 명확한 합성 얼굴)만 써야 한다. 고객사 담당자 얼굴 사용 시 필요한 것: 본인 서면 동의(초상권·퍼블리시티권), 사용 범위·기간, 퇴사·철회 시 중단 절차, 딥페이크 오남용 방지 조항 — 전부 법무·계약 사항. 기술 요건은 정면 상반신, 얼굴 크게, 512 크롭(§4-5).
- **기획자가 하면 안 되는 말**: "원하시는 분 얼굴로 바로 만들어 드립니다."

### 9. 범위·대안

#### Q9-1. "부적합" 판단과 "PoC 성공" 보고, 무엇이 성공인가
- **한 줄 답**: 성공한 것은 **"GPU 1대에서 아바타 1명이 텍스트를 받아 실시간으로 말하는 영상을 만들고 그 파이프라인이 Modal 위에서 돈다"**까지이고, "1000 대화형 세션을 이 구조로 자체 운영"은 09-14에 부적합으로 판단했다 — 두 메시지는 충돌하지 않고 범위가 다르다.
- **확신도**: 실측·판단 기록(§3, §4, §10).
- **상세**:

| PoC가 증명한 것(실측) | 증명하지 않은 것 | 부적합하다고 판단한 것 |
|---|---|---|
| Lite: L4 1대에서 0.96 s 청크를 실시간(1.18×) 생성, 벽시계 동기 유지 | 마이크 → STT → LLM → TTS → 아바타 "대화"(0회) | 현재 구조로 동시 1000 대화형 세션 자체 운영 |
| Pro: 2×H100에서 1.65× 생성, 화질 우수 | 지원자 발화 끝 기준 응답 지연 | Pro 1000 세션(H100 2000장, $7,900/hr) |
| 텍스트 입력 → 화면 6~7 s(예열 컨테이너) | 한국어 입모양 정확도 | — |
| 콜드 스타트 85~125 s, 비용 단가, 리전별 배정 시간 | 30~60분 안정성, 다중 아바타 품질 | — |
| Modal 위에서 예열·큐·HLS 파이프라인이 동작 | 동시 세션 2개 이상, 재접속·복구 | — |
| 30분 GPU 원가 Lite $0.40 / Pro $3.95 | 총원가(TTS/STT/LLM/전송) | — |

적합하다고 본 용도(§10): 방송·비동기(사전 렌더), 소수 프리미엄 세션. 경영진 문장: "발화 렌더 PoC는 성공. 대화형·대규모는 다음 단계의 검증 과제."
- **기획자가 하면 안 되는 말**: "PoC가 성공했으니 1000 세션도 시간 문제입니다."

#### Q9-2. 하이브리드(사전 렌더 + 실시간)
- **한 줄 답**: 사전 렌더(Pro)와 실시간(Lite)을 섞으면 **화질 차이(선명도 1.8배)가 전환 순간 눈에 띌 가능성이 높다** [추정] — 그리고 GPU 비용은 "실시간 구간에만 GPU를 빌리는 시간 다중화 풀"을 구현해야 실시간 비율만큼 줄고, 그냥 세션 내내 GPU를 잡고 있으면 하나도 안 줄어든다.
- **확신도**: 화질 차이는 실측(§4-5), 체감은 추정. 비용 절감 산술은 전제(풀 구현) 위의 추정. 시연은 [추정] 1~2주면 프로토타입 가능.
- **상세**: 전환이 안 보이게 하려면 (a) 사전 렌더도 Lite로 같은 화질을 맞추거나, (b) 실시간 구간을 음성만(정지 아바타/미세 움직임 루프)으로 처리하는 것이 현실적이다. 비용·GPU 수 산술(1000명이 동시에 면접, 세션 30분, 전제: 실시간 구간에만 예열 풀에서 GPU를 빌리고 반납하는 스케줄러가 있음 — 미구현):

| 실시간 비율 | 동시 필요 GPU [산술] | 시간당 GPU 비용(Lite) | 비고 |
|---|---|---|---|
| 100% | 1000 | ≈$800 | 현재 구조 |
| 50% | ≈500 | ≈$400 | 풀 스케줄링 필요, 전환 지연 발생 |
| 20% | ≈200 | ≈$160 | 서울 200대 확보 [모름] |
| 0%(음성만) | 0 | $0 | §13-4, TTS/STT/LLM 비용만 |

콜드 스타트 85~125 s 때문에 "꼬리질문마다 GPU를 새로 켜는" 방식은 불가하고, 예열된 GPU를 짧게 빌리는 풀이 있어야 한다. 그 풀 자체가 세션 관리·다중화의 핵심 난제라 파일럿 뒤의 과제다. 사전 렌더 부분은 지금도 만들 수 있고(Pro를 L4에서 최종 렌더 전용으로, §4-2), 비용은 렌더 1회분이다.
- **기획자가 하면 안 되는 말**: "하이브리드로 하면 비용이 1/5로 줍니다."

#### Q9-3. 음성만, Light2D
- **한 줄 답**: **음성만(정지 아바타 + 목소리)은 GPU가 0대라 1000 동시의 병목이 TTS/STT/LLM 벤더 한도로 옮겨가고**, Light2D(브라우저에서 소리 크기로 입 레이어 4단계를 바꾸는 방식)도 GPU 0대이지만 **음소 정확도가 없어 "말하는 그림" 수준**이다 — "실사 아바타 면접"으로 팔 수는 없고 "AI 면접관(음성 중심)"으로는 팔 수 있다고 본다.
- **확신도**: 구조 사실(§13-3, §13-4). 벤더 한도 [확인 필요]. Light2D 시연은 [추정] 수일(OpenTalking 구성에 있음).

| 방식 | 화질/자연스러움 | 지연(발화 끝 기준) [추정] | 1000 동시 | GPU 비용/세션·hr |

| 음성만 + 정지 사진 | 움직임 없음 | STT+LLM+TTS만 ≈ 2~4 s | 벤더 한도 내 가능 [확인 필요] | $0 |

- **기획자가 하면 안 되는 말**: "Light2D도 아바타니까 같은 상품입니다."

#### Q9-4. 상용 API 구매

- **기획자가 하면 안 되는 말**: "HeyGen 쓰면 바로 1000 동시 됩니다."

### 10. 데모·영업

- **상세**:

| Lite/Pro 나란히 비교 영상 | 한국어 입모양 테스트 결과 공개 | 1시간 연속 안정성 보증 |
| 콜드 스타트 vs 예열 차이 설명 | 아바타 3~4종 비교 | 재접속·장애 복구 시연 |

데모 시나리오 초안: (1) 소개 영상(Pro 녹화, 화질 조건 자막), (2) 라이브: 운영자가 준비된 면접 질문 3개를 입력, 아바타가 말함 — "지금은 운영자가 질문을 입력하는 방식이고, 음성 대화 데모는 12월 예정"이라고 먼저 말한다, (3) 고객이 "제가 질문해 볼게요" 하면: 운영자가 그 문장을 그대로 타이핑해 아바타가 말하게 하고, 대답 생성(LLM)은 아직 붙지 않았다고 설명한다. 이렇게 말하면 속인 것이 되지 않는다.
- **기획자가 하면 안 되는 말**: "마이크로 직접 대화해 보세요."

#### Q10-2. 라이브 데모 실패 확률과 백업
- **한 줄 답**: 실패 확률 수치는 **없다**(통계가 없다) — 실패 원인은 알려져 있고(예열 안 됨·GPU 미배정·회의실 네트워크·배포 함정), **T−60분부터 체크리스트를 밟고 녹화 백업을 준비하면** 임원 데모를 잡을 수 있다고 본다.
- **확신도**: 원인은 실측(§4-3, §6, §7). 확률은 모름(확인: 데모 리허설 10회 기록, 비용 10 × ~$2).
- **상세**: 원인과 대비 —

| 실패 원인 | 대비 |
|---|---|
| 컨테이너 콜드 스타트 85~125 s 중 데모 시작 | T−60분 예열, 준비 플래그(심장박동) 확인 |
| 서울 GPU 미배정 | T−60분에 서울 실패 시 도쿄로, 그래도 실패 시 미국(지연 증가) — 순서대로 시도 |
| 유휴 600 s 후 컨테이너 종료 | 라이브 세션을 데모 내내 열어둔다(무음 청크가 계속 생성돼 유휴 아님) |
| 누군가 그날 배포·Stop | 데모 당일 배포 금지, 데모 전용 앱 분리 |
| 회의실 네트워크(방화벽·Wi-Fi) | HLS는 HTTPS라 대체로 통과 [추정]. 노트북 LTE 테더링 예비 |
| 우리 스튜디오 서버(현재 Mac 1대) | 데모용 노트북 사전 점검, 동일 구성 예비 노트북 |
| TTS(macOS say) 4 s 기동 지연 | 문장을 미리 짧게, 첫 문장은 미리 재생해 워밍업 |

체크리스트: T−60 예열 시작·플래그 확인 / T−30 실제 문장 1개 렌더해 화면 확인 / T−10 네트워크·플레이어 재확인, 백업 영상 열어두기 / T−0 라이브. 백업: Pro·Lite 녹화 영상(화질·조건 자막 포함), 실패 시 "지금 GPU 배정이 지연되어 녹화본으로 보여드립니다"라고 말하고 넘어간다.
- **기획자가 하면 안 되는 말**: "라이브 데모는 항상 됩니다."

#### Q10-3. 자료에 쓸 수 있는 문구의 선
- **한 줄 답**: 녹화 영상은 **화질(Pro/Lite)·장비·날짜·"텍스트 입력, 대본 기반"을 자막으로 명시**하면 쓸 수 있고, "실시간 대화형"은 대화 루프가 시연되기 전까지 **쓸 수 없다** — "실시간 렌더"는 조건을 붙이면 가능하다.
- **확신도**: 실측 범위 기준의 판단.
- **상세**:

| 쓸 수 있는 문구 | 쓰면 안 되는 문구 |
|---|---|
| "아바타 발화 영상을 GPU에서 실시간으로 생성(0.96초 단위)" | "실시간 대화형 AI 면접관"(대화 루프 없음) |
| "텍스트 입력 후 6~7초 내 아바타 발화(예열된 서버, 개발 환경 측정)" | "3초 응답" / "즉시 응답" |
| "Pro 화질 시연(2×H100). 대규모 서비스 화질은 별도 안내" | Pro 영상만 보여주고 화질 언급 없음 |
| "한국어 음성 아바타(입모양 정확도 검증 중)" | "한국어 발음에 정확히 맞는 입모양" |
| "현재 단일 세션 PoC 단계, 단계적 확대 계획" | "동시 1000명 지원" |
| "Apache-2.0 오픈소스 엔진 기반" | "라이선스 이슈 없음" |
| "GPU 연산은 서울 리전(옵션)" | "데이터 국내 보관" |

녹화 영상 주석 예: "FlashHead Pro / 2×H100(도쿄) / 2026-09-14 녹화 / 텍스트 입력, 대본 기반 / 실시간 렌더 출력을 녹화 / 서비스 화질·지연은 상품 구성에 따라 다름". Lite 영상에도 같은 형식으로.
- **기획자가 하면 안 되는 말**: "이 영상이 실제 서비스 화면입니다."

#### Q10-4. 데모 비용과 대본
- **한 줄 답**: 데모 1회(예열 1시간 + 미팅 1시간) GPU 비용은 **Lite ≈ $2(≈ ₩2,800), Pro ≈ $17(≈ ₩24,000)**(산술) — 영업이 자유롭게 돌리는 것은 "끄는 것을 잊으면 하루 $19/대"라 **안 되고**, 데모는 개발팀이 켜고 끄는 예약제로 하며, 지금 대화는 **미리 짠 대본**이다(LLM 에코).
- **확신도**: 단가 실측·산술(§4-4). 운영 규칙은 제안.
- **상세**: 산술: Lite 2 h × $0.80 + 꼬리 $0.13 ≈ $1.73; Pro 2 h × $7.90 + $0.66 ≈ $16.5. CPU/메모리 ~$0.1/hr 추가. 규칙(초안): (1) 데모 앱은 운영 앱과 분리, `max_containers`를 데모 수만큼만, (2) 데모 요청은 전날까지, 개발팀이 T−60 예열·종료 담당, (3) 유휴 자동 종료 600 s는 유지(라이브 세션이 열려 있으면 유휴가 아니므로 세션 종료를 반드시 확인), (4) 주간 청구 리포트 공유. 대본: LLM이 에코 상태이므로 "면접관 질문 → (지원자 답) → 다음 질문"을 운영자가 순서대로 입력하는 대본 데모다. 고객에게 "질문 생성은 대본, 아바타 발화 영상은 실시간 생성"이라고 정확히 말해야 한다.
- **기획자가 하면 안 되는 말**: "아바타가 지원자 답을 듣고 스스로 다음 질문을 만들고 있습니다."

## B. 기획자의 오해 12개 — 개발팀의 교정 문장

각 항목: 오해 → **대신 이렇게 말해달라**(한 문장).

1. "1개가 되면 1000개는 서버만 늘리면 된다."
   → **"세션 1개당 GPU 1대가 필요한 구조이고, 서울에서 6대 동시 확보도 실패한 적이 있어 1000대 확보는 계약과 구조 변경이 먼저입니다."**
2. "3초 = 지원자가 말을 끝내고 3초 뒤 아바타가 대답한다."
   → **"텍스트를 넣은 뒤 화면에 아바타가 말하기까지 6~7초이고, 음성 인식과 답변 생성을 붙이면 현재 구조로는 8~12초 추정입니다."**
3. "PoC에서 대화가 됐다."
   → **"PoC는 '텍스트를 주면 아바타가 말한다'까지이고, 마이크로 대화한 적은 아직 없습니다."**
4. "GPU는 아바타가 말할 때만 쓰니 비용은 발화 시간에 비례한다."
   → **"세션이 열려 있는 동안은 아바타가 듣고만 있어도 GPU 요금이 계속 나갑니다(30분 면접 = 30분 GPU)."**
5. "더 좋은 GPU를 쓰면 더 빨라진다."
   → **"지연의 대부분은 음성 합성·답변 생성·전송 구조에서 나오고, GPU를 올려도 체감 속도는 거의 안 바뀝니다."**
6. "데모에서 본 Pro 화질이 서비스 화질이다."
   → **"Pro는 세션당 H100 2장($7.90/hr)이 필요해 대규모에서는 Lite(입술 뭉개짐)가 현실적 후보이며, 자료에는 어느 화질인지 반드시 표기합니다."**
7. "면접 1건 $0.40이면 원가는 거의 없다."
   → **"$0.40은 GPU만이고, 음성 인식·합성·LLM·전송·예열·장애 재시도·인건비가 더해진 총원가는 벤더 견적 후에 나옵니다."**
8. "Modal은 큰 클라우드니까 용량은 늘 있다."
   → **"GPU 용량은 순간마다 변하고 우리 동시 한도(쿼터)도 미확인이라, 공채 물량은 사전 계약과 예약으로만 확보할 수 있습니다."**
9. "만든 팀이 운영도 할 수 있다."
   → **"PoC는 만들었지만 GPU 스트리밍 서비스를 운영해본 사람이 팀에 없어, ML 서빙·미디어·SRE 인력 없이는 운영 일정을 약속할 수 없습니다."**
10. "세션은 클릭하면 바로 시작된다."
    → **"미리 켜두지 않으면 세션 준비에 85~125초가 걸리므로, 면접은 예약 시간 기준으로 사전 예열하는 운영이 전제입니다."**
11. "GPU가 서울에 있으니 데이터는 국내에 있다."
    → **"GPU 연산은 서울에서 하지만 Modal은 미국 기업이라 제어·로그·큐의 위치와 국외 이전 해당 여부는 확인 중입니다."**
12. "오픈소스라 라이선스 문제는 없다."
    → **"핵심 엔진은 Apache-2.0으로 상용 가능하지만, 오디오 인코더 체크포인트 라이선스와 아바타 얼굴의 초상권은 별도 확인이 필요합니다."**

## C. 외부 질문 8개 — 개발팀 제안 답변 초안

각 답변 앞의 표시: **[약속 가능]** / **[조건부]** / **[불가]**.

1. **경영진**: "이번 분기 안에 영업 자료(데모 영상 + 가격표 초안)를 만들 수 있나?"
   **[조건부]** 데모 영상은 이번 분기에 만들 수 있습니다 — 단 "Pro 화질·2×H100·텍스트 입력·대본 기반"처럼 조건을 자막으로 넣고, "실시간 대화형"이라는 문구는 대화 루프 시연 전이라 쓰지 않습니다. 가격표는 GPU 원가(30분 Lite ≈ $0.58, Pro ≈ $4.66, 꼬리·CPU 포함)까지는 지금 나오고, 음성 인식·합성·LLM·전송 원가는 벤더 견적(2주) 뒤에 채워집니다. 따라서 "가격표 초안"은 분기 내 가능하지만 "확정 단가"는 아닙니다.

2. **경영진**: "고객 두 곳에 내년 상반기 공채 사용을 약속해도 되나? 어느 규모로?"
   **[조건부]** "동시 1000·완전 대화형"은 상반기에 약속할 수 없습니다. 약속 가능한 형태는 "한 고객사와 소규모 파일럿(동시 50 이하, 일부 직군·일부 일정, 예약제)을 상반기에 함께 검증하고 하반기 확대"이며, 이것도 ML 서빙 인력 합류(11월), 인프라 쿼터·벤더 계약(10~11월), 법무 검토(12월)가 전제입니다. 조건이 하나라도 늦으면 규모는 10 이하로 줄어듭니다.

3. **고객사 A 채용팀**: "우리 공채 1차는 하루에 지원자가 몇백 명 단위다. 같은 시간대에 동시에 면접이 되나? 대기 시간은?"
   **[불가(현재) → 조건부(내년 하반기)]** 현재 검증된 동시 세션은 1개이며, 같은 시간대 수백 명 동시 아바타 면접은 내년 상반기에는 제공할 수 없습니다. 상반기에 가능한 것은 예약 슬롯 방식(시간대별 동시 50 이하)이고, 예약 시간에 맞춰 서버를 미리 준비하므로 정상 시 대기는 거의 없지만, GPU 확보 실패 시 음성 중심으로 전환되는 조건을 계약에 명시해야 합니다. 수백 명 동시는 음성 중심(아바타 정지 이미지) 방식이면 검토 가능합니다 — 이 경우 병목은 음성 인식·합성 벤더의 동시 한도이며 확인 중입니다.

4. **고객사 B 보안팀**: "지원자 영상·음성이 어디에 저장되고 국외로 나가나? DPA와 보안 질의서에 답할 수 있나?"
   **[조건부]** 아바타 영상 생성(GPU 연산)은 서울 리전에서 수행하도록 지정할 수 있습니다. 그러나 인프라 제공사(Modal, 미국)의 제어·로그 경로와 음성 인식·LLM·음성 합성 벤더의 처리 위치는 확정 중이며, 확정된 데이터 흐름도는 2주 내 제공합니다. 보안 질의서는 구성도·오픈소스 목록·연산 위치는 지금 답할 수 있고, 접근 통제·암호화·감사 로그·사고 대응·DPA는 준비 중이며, ISMS-P와 SLA 수치는 현재 답할 수 없습니다.

5. **영업**: "면접 1건당 얼마로 제안하면 되나? 상용 아바타 API를 쓰는 경쟁사 대비 우리 강점은?"
   **[불가(현재)]** 단가 제안은 총원가가 나오기 전이라 지금 할 수 없습니다 — GPU 원가만 30분 Lite ≈ $0.58, Pro ≈ $4.66이고, 여기에 음성 인식·합성·LLM·전송·예열·장애 재시도(모두 미확정)가 더해집니다. 경쟁사 대비 강점 주장도 상용 API의 가격·지연·한국어 성능을 확인한 뒤(2주)에만 말할 수 있습니다. 지금 말할 수 있는 차별점은 "오픈소스 엔진으로 연산 위치·아바타·비용 구조를 우리가 통제한다"는 구조적 특성이며, 이것도 데이터 흐름도 확정 후에 쓰십시오.

6. **CFO**: "월 인프라 비용 상한은 얼마인가? 최악의 경우는?"

## D. 개발팀의 핵심 메시지 5개

1. **PoC가 증명한 것은 "GPU 1대에서 아바타 1명이 텍스트를 받아 6~7초 뒤 말하는 영상을 실시간으로 만든다"까지다.** 대화(마이크→답변)는 0회, 동시 세션은 1개, 한국어 입모양·1시간 안정성은 미측정이다.
2. **지연의 병목은 GPU가 아니라 음성 합성·답변 생성·전송 구조다.** STT·LLM을 붙이면 현재 구조로 8~12초 [추정]이고, 3~5초대는 WebRTC·스트리밍 TTS를 구현한 뒤의 목표치다. 비싼 GPU를 사도 이 숫자는 거의 안 줄어든다.
3. **비용은 "세션이 열린 시간 × GPU 1대"이고, 1000 동시는 L4 1000대(≈ $800/hr, GPU만)다.** 확보 가능 여부는 미확인이며, 서울에서 6대 동시도 실패한 적이 있다. 총원가는 벤더 견적 후에 나온다.
4. **내년 상반기에 약속할 수 있는 최대는 "한 고객사, 동시 50 이하, 예약제 파일럿"이고, 그것도 ML 서빙·미디어·SRE 인력 합류, 인프라·벤더 계약, 법무 검토가 10~12월 안에 끝나야 한다.** 1000 완전 대화형은 이 팀·이 구조로 상반기 불가.
5. **개발팀 추천은 "음성 우선 대화 루프를 먼저 만들고, 아바타(Lite)는 소규모 프리미엄 계층으로 단계 확대, 1000 규모 아바타는 구매 옵션과 다중화 검증 결과로 12월에 결정"이다.** 이렇게 하면 상반기에 고객에게 줄 것이 생기고, 아바타 확대 여부는 사실 확인 뒤에 정할 수 있다.

### 개발팀 추천안과 이유

**추천: §13-5 단계적 + §13-4 음성 우선 폴백을 기본 구조로, 아바타(Lite)는 파일럿→50 규모의 프리미엄 계층으로 올리고, 1000 규모 아바타는 12월에 "다중화 검증 결과 + 구매 조사 결과"로 결정한다.**

이유: (1) 지연·비용·용량의 병목이 전부 GPU 렌더가 아니라 대화 루프와 인프라 확보에 있으므로, 대화 루프를 먼저 만들면 어떤 아바타 방식을 택해도 재사용된다. (2) 음성 우선 구성은 GPU 0대라 지금 팀 역량(백엔드·프론트·DevOps)으로 1000 동시의 길이 있고, 상반기에 고객에게 줄 것이 생긴다. (3) 아바타 규모 결정에 필요한 사실(쿼터·다중화·한국어 입모양·상용 API)이 2~4주 안에 나오므로, 지금 결정하는 것보다 12월에 결정하는 것이 틀릴 확률이 낮다. 대안별 장단점은 Q9-2·Q9-3·Q9-4와 §13에 있다 — 구매는 빠르지만 데이터·비용 통제가 약하고, 하이브리드는 전환 화질 문제와 풀 스케줄러 난제가 있고, Light2D는 GPU 0대이지만 실사 아바타로는 팔 수 없다.

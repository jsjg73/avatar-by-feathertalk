# GPU 다중 요청 처리 착수 요청서

에이전트를 바꿔가며 (Claude Code 가 아닌 다른 도구로도) GPU 박스에 "N 개 동시 요청을 처리해줘" 를 시킬 때, 매번 같은 시행착오를 겪지 않기 위한 문서. FeatherTalk 동시 세션 벤치마킹(2026-09-29)에서 실제로 겪은 실수들을 이식 가능한 형태로 정리했다 — Claude Code 세션 메모리(`feedback-gpu-multi-request-serving`)에도 같은 내용이 있지만, 그건 이 세션에만 남는다. 이 문서는 어느 에이전트에게든 그대로 붙여넣을 수 있다.

---

## 1. 용어 — 이렇게 말하면 에이전트가 바로 정석 설계로 간다

| 하고 싶은 말 | 쓸 용어 | 왜 이 용어인가 |
|---|---|---|
| "GPU 하나로 여러 요청을 처리해줘" | **producer-consumer serving** / **model server 구조** | Triton, TorchServe, vLLM 이 다 이 이름의 아키텍처를 쓴다. 이 단어를 안 쓰면 에이전트는 십중팔구 "요청마다 프로세스 하나" 로 간다 |
| "요청마다 배치로 묶어서 GPU 호출 한 번" | **continuous batching** / **iteration-level batching** | LLM 서빙(Orca, OSDI 2022)에서 온 표준 이름. "배치 처리" 라고만 하면 에이전트가 스레드풀로 흉내만 내다 끝나는 경우가 있었다 |
| "프로세스마다 GPU 컨텍스트 잡지 마" | **N separate CUDA contexts 금지** | 프로세스당 고정 400–500MB VRAM 오버헤드가 있고, 모델 크기와 무관하다. 이 표현을 안 쓰면 에이전트가 그냥 `multiprocessing` 으로 N개 띄우고 끝낸다 |
| "같은 데이터/모델을 프로세스마다 중복 로딩하지 마" | **shared read-only memmap** (`np.memmap`, OS page cache 공유) | 공유해야 할 자산을 프로세스별 메모리에 캐시하면 N=1 에서 빨라 보여도 N=2+ 에서 OOM 난다 |
| "몇 세션까지 되는지 재줘" | **concurrency sweep** — N 을 늘려가며 최소/평균/최대 처리량을 real-time 목표와 비교 | 1회성 벤치 말고 재실행 가능한 스크립트를 요구하는 표현 |
| "박스에 올릴 때 로컬 찌꺼기 빼줘" | **clean deploy** — `.venv`/`.git`/`__pycache__`/`.DS_Store` 제외, `git archive` 또는 `rsync --exclude` | 특히 `uv` 로 만든 로컬 venv 가 섞이면 원격에서 심볼릭 링크가 로컬 macOS 절대경로를 가리켜서 조용히 깨진다 |

## 2. 복붙용 착수 요청 (한글)

작업을 시킬 때 아래 문단을 그대로 붙여넣는다. 대괄호만 채운다.

> [작업 내용]을 GPU 박스([박스 사양])에서 서빙하려고 한다. 목표 동시 처리 수는 **N=[숫자]** 다.
>
> 다음을 기본값으로 삼아줘:
> 1. N 개 요청마다 별도 프로세스 + 별도 CUDA context 를 만드는 방식 말고, **producer-consumer / model server 구조**(CPU 전처리는 병렬 워커, GPU 는 단일 프로세스가 배치로 처리)를 먼저 검토하고, 왜 그게 맞는지/안 맞는지 (N 이 작아서 오히려 오버킬인지) 판단해서 알려줘.
> 2. 코드를 스케일링하기 전에 **워커당 메모리(RAM/VRAM) × N 이 박스 실제 용량을 넘는지 먼저 계산**해줘. 여러 워커가 같이 쓰는 자산(모델 가중치, 데이터셋, 임베딩 등)은 워커마다 중복 로드하지 말고 `np.memmap` 공유 캐시나 별도 서버 프로세스로 한 번만 로드해줘.
> 3. 박스에 코드를 올릴 때 `.venv`/`.git`/`__pycache__`/`.DS_Store` 를 제외한 **clean deploy** 로 올려줘.
> 4. 코드 짜기 전에 먼저 **재실행 가능한 동시성 측정 스크립트**부터 만들고, 그걸로 변경 전/후를 비교해줘. 한 번 돌린 숫자 하나를 결론으로 삼지 마.

## 3. 착수 전에 에이전트가 스스로 답해야 할 질문 (체크리스트)

코드를 쓰기 전에 아래에 답이 없다면, 붙여넣은 요청문을 에이전트가 제대로 못 읽은 것이다.

- [ ] 목표 동시성 N 은? (N=8 이면 producer-consumer 서버는 과할 수 있다. N=50+ 면 거의 필수다)
- [ ] 워커/세션마다 공유해야 할 자산은 무엇이고, 지금 설계에서 몇 번 로드되는가?
- [ ] (워커당 메모리) × N 계산값과 박스의 실제 RAM/VRAM 을 비교했는가?
- [ ] N 개 프로세스가 각자 CUDA context 를 잡는 구조인가, 아니면 GPU 를 하나의 프로세스가 소유하고 배치하는 구조인가? 전자라면 왜 그걸 선택했는가?
- [ ] 박스에 올리는 아티팩트에 로컬 전용 파일(venv, .git, 캐시)이 섞여 있지 않은가?
- [ ] 변경 전/후를 비교할 재실행 가능한 측정 스크립트가 있는가, 아니면 1회성 숫자만 있는가?

## 4. 흔한 함정 — "절반만 한" 최적화가 역효과를 낸 사례

producer-consumer 구조의 **절반만** (예: CPU 전처리를 병렬 워커로 안 돌리고 `ThreadPoolExecutor` 로만 감싼 뒤, GPU 호출만 배치로 묶기) 구현하면, N-프로세스 방식보다 **더 느려질 수 있다.** 실제로 겪은 수치: naive N-프로세스 baseline 대비 N=1 에서 -58%, N=8 에서 -69%. 원인은 진짜 OS 수준 병렬성(멀티프로세싱이 CPU-bound 전처리에 공짜로 주던 것)을 걷어내면서, 아직 그걸 대체할 병렬 전처리 워커는 없었기 때문이다. 이 이득은 **CPU 쪽 병렬성을 진짜로 복원 + GPU 쪽 배치 공유**를 **둘 다** 갖춰야 나온다.

## 5. N개를 실제로 동시에 띄웠을 때만 나오는 함정 둘

**(a) 워커별 리소스 경로를 `os.getcwd()`만으로 만들지 마라.** N개 워커가 같은 cwd 에서 뜨면 전부 똑같은 경로로 계산되고, 그 경로를 시작할 때마다 "안의 파일 전부 지우고 새로 생성"하는 코드가 있으면 **나중에 뜬 워커가 먼저 뜬 워커의 FIFO/소켓/파일을 지워버리고 자기 걸로 바꿔치기**한다. 증상은 CPU/메모리 경합처럼 보이는 산발적 데이터 오염(FeatherTalk 사례에서는 서로 다른 워커의 영상 프레임이 섞여서 화면이 깨짐)이라 진단이 오래 걸린다. N=1 로 혼자 띄우면 절대 안 나타난다. 해결: 워커별 리소스 경로엔 반드시 포트나 PID 같은 그 워커만의 고유값을 넣는다. "혼자 띄우면 멀쩡한데 여러 개를 같이 띄우면 서로 오염되는" 증상을 보면 CPU/메모리 이론보다 공유 경로부터 의심한다.

**(b) 프로세스/스레드 수를 늘리기 전에 컨테이너의 cgroup `pids.max`를 확인한다** (`cat /sys/fs/cgroup/pids.max`, `pids.current`). `ulimit -u`는 "unlimited"라고 나와도 Docker 컨테이너 자체에 호스트가 건 상한이 따로 있을 수 있다. GPU 워커 하나가 BLAS/OMP/torch 스레드를 여러 개씩 만드므로, N이 커지면 이 상한에 먼저 걸린다 — 증상은 `pthread_create failed: Resource temporarily unavailable`, `bash: fork: retry` 같은 일반적인 자원 부족 메시지라 원인 파악이 늦어진다. 렌트한 박스마다 호스트가 달라 이 값도 다를 수 있으니, 새 박스를 빌릴 때마다 다시 확인한다.

## 관련

- Claude Code 세션 메모리: `feedback-gpu-multi-request-serving` — 같은 내용의 Claude Code 전용 기록, FeatherTalk 실측 수치(N≤8 → N≤24, 3배) 포함.
- [`../capacity/README.md`](../capacity/README.md) — 이것과는 다른 종류의 문제(동시 세션의 GPU 점유 시간이 짧을 때의 통계적 다중화/큐잉 이론)를 다룬다. 이 문서는 "한 요청이 GPU 를 오래 붙잡는 배치 서빙" 쪽, 그쪽은 "발화 순간에만 짧게 GPU 를 쓰는 다중화" 쪽이다.
